# PACI取込の完全性と復旧

2026-11-28: 展開allowlistからZEDが漏れ、元ZIPにある過去走が欠落していた。対象日の評価キャッシュも入力更新だけでは再計算されなかった。

## 自動で確認すること

- ZIP内の全ての年月日付きテキストを保存し、ファイル名・行数・SHA256・処理区分をmanifestに記録する。未知形式も捨てず `retained-only` と明示する。
- ZED/SEDがなければ完全性確認を失敗にする。各行の馬ID・開催日・レースIDと距離・頭数・着順を派生DBへ照合し、1件でも不足・不一致があれば公開用DBを置き換えない。
- 対象開催のキャッシュ評価を派生DB内で再計算する。元DBは読取専用、最後の正常な派生DBを保持する。
- 常駐取得は監査未実施の旧ソースを検知し、取得予定に支障のない時間帯に再準備する。未検証ソースは正常完了にせず `source_unverified` を通知する。statusに `sourceIntegrity` の照合件数を付ける。

## 毎開催の確認

1. PACI取得後、prepared-source.jsonの `historyAudit.complete=true` と expectedRows=verifiedRows を確認する。
2. `files` の全件と `retainedOnly` を確認する。JOAと基準オッズ類は原本保存とDB取込を区別し、未解析項目を「表示・解析済み」としない。
3. 予定レース数・出走頭数・過去走の有無を全頭で照合する。過去走0件は原本にない場合と取込欠落を区別する。カタログ表示は直近5走で、原本・詳細DBには全収録行を保持する。
4. 本番同期後、全レースの過去走と統計を再読取して派生DBと比較する。送信成功だけで完了にしない。
5. 当日オッズ・パドック・馬体重・結果は別途取得時刻と提供有無を確認する。未公開・契約対象外・取得失敗を推測で埋めない。

## 取り直し

- 同一JRDBアカウントの取得プロセスを重複起動しない。常駐を一時停止し、全レース取得後に再開する。
- 本番DB、常駐ソース、モデル、予想・購入・精算、既存観測を退避する。
- 入力を修正した日時で追記同期する。以前の予想・購入・観測の取得日時を遡らせない。購入済み記録の訂正も勝手に行わない。
- 公開用DBは対象開催だけ更新し、他開催を保存する。変更直前のハッシュ一致を確認し、変更後の読取ハッシュと内容を照合する。
- 失敗時は前のruntimeとprepared-source.jsonへ戻す。購入台帳と観測は追記型なので削除しない。復旧を理由に当時の予想確率を書き換えない。

## 限界

取得可能なのは提供されたファイルと契約内の画面項目。元にない項目や未対応形式の全フィールドを解析済みとは扱わない。旧インポータは中央以外のレースキーの一部を数値へ正規化するため、元のキーは保存原本を正本として残す。
