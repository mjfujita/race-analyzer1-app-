# オッズのグループと買い目の比較

## 目的と到達点

人気のまとまり・能力材料・着順の仮説を分けて判断する。「Aは上位候補」を２着固定へ自動変換しない。
今回の範囲はグループ作成、取得済み能力の参照、着順・券種・予算の比較、追記保存、購入・精算、結果照合まで。
既存PACI、モデル、軸選択、認証・権限、最初にやることを維持する。新しい勝率モデルや自動購入は作らない。

## 操作

1. レースを開き、分析メニューの「グループ・買い目」を選ぶ。
2. 単勝の観測時点と区切り倍率を選ぶ。初期値は隣接オッズ比1.5。最適化済みの閾値ではない。
3. 「○番の前で区切る」で境界を調整する。同倍率は分割しない。自動案の境界も保持する。
4. 各馬のIDM・近い距離・同場同距離実績・取得過去走を確認する。未取得は未取得と表示し、確率に置き換えない。
5. １〜３着のグループを指定する。候補から外す馬は明示的にチェックを外す。
6. 指定順の３連単、２・３着入替、同じ候補の３連複、馬単を比較する。
7. 予算上限（最大１万円）・基本金額・各買い目の金額を調整する。０円指定で除外できる。超過時は保存しない。
8. 必要なら組合せの実オッズと観測日時を入力する。全点の価格がないと最低払戻は未算出。単勝から組合せ価格を推定しない。
9. 根拠と不確かな点を記入し、案または見送りを固定保存する。保存は購入にならない。
10. 実購入・正式払戻は別途記録する。既存の訂正・返還確認・HJC照合を再利用する。
11. 結果到着後、候補の不足・着順の不一致・配分の影響を分けて見る。

## 時刻・学習・統計

- 選択オッズ、比較元の早い観測、手動調整前後の境界、能力材料の表示内容、除外馬、全配分を固定する。
- 全出走馬の実オッズが必要。取消を含む編成では保存を保留する。
- 締切は発走10分前。保存が締切後、価格の時刻証跡が不足、組合せ価格の取得が後日なら過去検証とする。
- サーバーは本人認証・正式な締切・取得済みの元オッズとの一致を確認し、間に合った案だけに変更不可の受領を発行する。
- 能力情報は取得済みの参考材料。新しい校正済み確率・期待回収率・黒字確率を生成しない。
- `groupPlans`は既存ledger v1の省略可能な追記コレクション。旧ファイルを維持する。人間のグループ判断には確率を捏造しない。
- グループ受領は`group-receipts`に分離。Pythonへの既存forecast receiptsはACE原案だけを返す。グループ判断は確率校正・モデル自動採用に入れない。
- 全体の振り返りは各レースの最後の受領済み案だけを集計する。過去検証・受領不明・見送り・同着・異常着順は的中率から除外する。
- Wilson 95%区間、対象数、精算済み実購入の回収率、最大１購入記録への払戻依存を表示する。同日・選択された標本は独立検証としない。
- A/Bの人数と価格帯はレースごとに異なる。A/Bの勝ち数から次レースの優位性や確率を自動加算しない。

## 技術変更と影響分析

- 主な実装：`groupAnalysis.js`、`GroupWorkspace.jsx`、`GroupReviewSection.jsx`。
- `forecastLedger.js`と認証付きcompanion APIで任意の`groupPlans`を追記・同期する。購入の`forecastId`は既存予想またはグループ案を参照できる。
- Python `group_plans.py`と`ledger.py`で同じデータを検証・結合する。従来の確率学習の入力は変更しない。
- 他タブの追記、ID競合、訂正の分岐、壊れた保存領域、同期失敗時の保全は既存方式を使う。
- API URL・認証方式・RLS・環境変数の変更なし。SQL schema/migrationなし。グループ案は既存private Storageの本人専用領域へ追記する。
- 既存の予想と購入は変更しない。全体の購入集計には、明示的に記録・精算したグループ購入も含まれる。

## 提出・本番反映の順序

作業ブランチ：`feat/odds-group-workspace`。基準は先行PR #9の`feat/axis-workspace-design`。
PR #8・#9が未マージのため、今回のPRは#9への積み上げとして差分を限定する。

本番未反映。反映する場合は次の順序を守る。

1. 先行PRを含めた変更を確認する。
2. collectorが参照するPython runtimeを本変更へ更新する。新しいグループ購入の参照を旧validatorでは読めないため、サーバー/UIより先に更新する。
3. 同じコミットのAPI・UIを候補環境で確認する。匿名401、別ユーザー403、本人の旧台帳の読取、グループ保存・購入・精算を確認する。
4. 本番反映時には既存のデプロイ手順に従う。実レースの事前判断を作る検証と架空データの動作確認を区別する。

既存のままロールバックする前に、グループ購入が存在するかを確認する。旧サーバー/旧PythonはgroupPlans参照の購入を解釈できない。
画面の問題なら新しい読取validatorとAPIを維持してグループ入口を非表示にする修正を優先する。記録を削除して旧形式へ戻すことはしない。

## 制約

- 組合せ価格の自動取得元は今回追加していない。手入力した実価格を使用する。
- 同着・取消・返還の自動的中判定は保留し、正式払戻で精算する。
- 多開催日の独立検証による収益性・確率精度は未確認。グループの閾値、能力の固定加点、着順パターンを学習済みとして扱わない。
